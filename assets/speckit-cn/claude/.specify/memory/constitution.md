# 项目宪章

## 核心原则

### 一、简单优先

- 优先最简单可用的方案；禁止为假想需求预留抽象层、配置项或扩展点。
- 引入任何新依赖、新模块、新模式前，必须证明现有结构无法承载当前需求。

### 二、测试先行（不可协商）

- TDD 强制执行：先写测试 → 确认测试失败 → 再写实现 → 转绿。
- 每个公开行为必须有对应测试；交付的测试套件必须能一键运行、独立于外部环境。

### 三、交付真实性（不可协商）

- 最终交付物禁止以桩函数、写死数据、演示输出、mock 响应冒充真实实现。
- 开发与测试过程中使用测试替身、临时桩、假数据照常允许——本原则约束交付物，不约束过程。
- 真实运行证据的要求粒度：每个用户故事检查点、以及交付前的 quickstart 验证，
  必须附真实运行的命令与输出；机械性中间任务不作要求。

### 四、中文优先

- 面向用户的提示、错误信息、帮助文本一律中文。
- 规格产物（spec/plan/tasks/宪章/清单）一律中文；源码标识符遵循所用语言的命名规范。

## 开发工作流

- 新功能一律走 SpecKit-CN 流程：定规则（可选）→ 提需求 → 需求变更（可选）→ 定计划 → 分任务 → 一致性分析（可选）→ 开始开发。
- 质量门禁（每次交付前）：全部测试通过 + quickstart 验收清单逐项真实运行通过 + 无残留占位任务。
- 每个用户故事独立可测试；实现完成后在对应检查点验证，再进入下一优先级故事。

- 本宪章是项目内最高约定，与任何其他文档冲突时以本宪章为准；analyze 环节将宪章冲突判定为最高严重度。

- 日常开发指引以规格产物（specs/ 目录）为准；规格与宪章冲突时宪章优先。
