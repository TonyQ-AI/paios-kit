> 适配自 [SpecKit-CN](https://github.com/chameleon-nexus/speckit-cn)（commit 0db9fa5）的 `claude/.claude/commands/需求变更.md`；主副本在 `{{ZCODE_DIR}}/speckit-cn`。

## 用户输入

用户输入 = 触发消息中技能名之后的文字（上游 `$ARGUMENTS`），作为澄清的优先级上下文。非空时必须先考虑。

## 本机执行约定

- 运行 `.ps1` 一律套静默包装：`python {{ZCODE_DIR}}/scripts/silent.py powershell -NoProfile -ExecutionPolicy Bypass -File <脚本> [参数...]`
- 项目根缺 `.specify/` → 先执行 `$speckit-cn-init` 流程再继续。
- spec 更新一律用 Edit 工具原子化写入，UTF-8，新增内容中文。

## Outline

目标：发现并削减当前功能规格中的歧义与缺失决策点，把澄清结论直接写入 spec 文件。

注意：本流程应在 `$speckit-cn-plan` 之前完成。用户明确跳过（如探索性 spike）可以继续，但须警告返工风险上升。

执行步骤：

1. 在项目根运行（**只运行一次**）`.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly`，解析最小 JSON 字段：
   - `FEATURE_DIR`、`FEATURE_SPEC`（可选记录 `IMPL_PLAN`、`TASKS` 备用）
   - JSON 解析失败 → 中止，提示用户先运行 `$speckit-cn-specify`，或检查 `.specify/feature.json` 是否指向正确的切片目录。

2. 读取当前 spec，按以下分类做结构化歧义与覆盖扫描，每类标注 Clear / Partial / Missing（形成内部覆盖图，除非一个问题都不问，否则不输出原图）：
   - **功能范围与行为**：核心目标与成功标准；明确的范围外声明；用户角色区分
   - **领域与数据模型**：实体、属性、关系；唯一性规则；生命周期/状态迁移；数据量假设
   - **交互与 UX 流**：关键用户旅程；错误/空态/加载态；无障碍与本地化
   - **非功能质量属性**：性能（延迟/吞吐目标）；可扩展性；可靠性与可用性；可观测性；安全与隐私；合规
   - **集成与外部依赖**：外部服务/API 及故障模式；导入导出格式；协议/版本假设
   - **边界与失败处理**：负向场景；限流；冲突解决（如并发编辑）
   - **约束与取舍**：技术约束；明确取舍或被否决的备选
   - **术语与一致性**：规范术语表；弃用同义词
   - **完成信号**：验收标准可测试性；可度量的完成定义
   - **杂项/占位符**：TODO 标记；未量化的模糊形容词（"健壮""直观"）

   对 Partial/Missing 的类别生成候选问题，除非：澄清不会实质改变实现或验证策略；信息更适合推迟到计划阶段（内部记下）。

3. 内部生成按优先级排序的候选问题队列（最多 5 个），约束：
   - 全程最多问 10 问（含追问）。
   - 每题必须可用二者之一回答：2-5 个互斥选项的单选；或 ≤5 字短语。
   - 只收录答案会实质影响架构、数据建模、任务分解、测试设计、UX 行为、运维就绪或合规验证的问题。
   - 覆盖面均衡：优先高影响未决类别；不为两个低影响问题浪费名额。
   - 排除已答、琐碎风格偏好、计划层执行细节（除非阻断正确性）。
   - 偏好能降低下游返工风险、防止验收测试错位的澄清。
   - 未决类别超过 5 个时，按（影响 × 不确定性）取前 5。

4. 顺序问答循环（交互式）：
   - **一次只问一题**。
   - 单选题用 Markdown 表格渲染选项：

     | Option | Description |
     |--------|-------------|
     | A | <选项说明> |
     | B | <选项说明> |
     | Short | 给出不同的简短回答（≤5 字）|（适用时才提供）

   - 简答题在问题后单列一行：`Format: Short answer (<=5 words)`。
   - 用户作答后：校验答案映射到选项或满足字数；含糊则追问消歧（仍算同一题，不前进）；满意后记入工作内存（暂不落盘），进入下一题。
   - 停止条件：关键歧义提前清零 / 用户示意结束（"done"、"没有了"、"继续"）/ 问满 5 题。
   - 不预告后续问题；开头就无有效问题则直接报告无关键歧义。

5. 每个答案被接受后立即增量整合：
   - 维护 spec 的内存表示 + 原始文件内容。
   - 本会话首个答案：确保存在 `## Clarifications` 章节（按模板放在最上层概述性章节之后；缺失则创建），并在其下建 `### Session YYYY-MM-DD`（今天）。
   - 紧接着追加一行：`- Q: <问题> → A: <最终答案>`。
   - 随即把澄清应用到最合适的章节：
     * 功能歧义 → 更新/新增功能需求条目
     * 交互/角色 → 更新用户故事或角色小节
     * 数据形态 → 更新数据模型（保持顺序，简洁记录新约束）
     * 非功能约束 → 在质量属性章节把模糊形容词改成度量或明确目标
     * 边界/负向流 → 在边界情形/错误处理下新增条目（无则创建）
     * 术语冲突 → 全文规范化术语（必要时一次性加注 `(原称 "X")`）
   - 新答案使早前的歧义表述失效 → 替换而非重复，不留矛盾的旧文本。
   - **每次整合后立即保存 spec 文件**（原子覆写，防上下文丢失）。
   - 保持格式：不重排无关章节；标题层级不变；插入内容最小化、可测试。

6. 校验（每次写入后 + 最终一遍）：
   - Clarifications 会话中每个被接受的答案恰好一条记录。
   - 已问（已接受）问题总数 ≤ 5。
   - 更新章节无残留的、本应由该答案消解的模糊占位。
   - 无矛盾的旧表述残留。
   - Markdown 结构有效；只允许新增 `## Clarifications`、`### Session YYYY-MM-DD` 两类标题。
   - 术语一致。

7. **使用中文更新规格**：更新内容写回 `FEATURE_SPEC`。**重要：所有新增和修改内容必须中文**。

8. 报告完成（问答循环结束或提前终止后）：
   - 已问已答题数；更新后的 spec 路径；触及的章节清单。
   - 覆盖摘要表：每个分类标注 Resolved / Deferred（超配额或更适合计划阶段）/ Clear / Outstanding（仍 Partial/Missing 但影响低）。
   - 有 Outstanding/Deferred 时，建议继续 `$speckit-cn-plan` 还是稍后再跑一次本技能。
   - 建议的下一个技能。

行为规则：
- 无实质歧义 → 回复"未发现值得正式澄清的关键歧义"并建议继续。
- spec 文件缺失 → 提示先运行 `$speckit-cn-specify`（本技能不新建 spec）。
- 永不超过 5 个已问问题（同一题的澄清追问不计新题）。
- 避免投机性的技术栈提问，除非其缺失阻断功能澄清。
- 尊重用户的提前终止信号（"停止"、"好了"、"继续"）。
- 全覆盖导致零提问时，输出紧凑覆盖摘要（全 Clear）并建议进入下一阶段。
- 配额用尽仍有高影响未决类别 → 在 Deferred 下显式标出并说明理由。
