# 经验原子沉淀与检索

知识库 = `{{PAIOS_ROOT}}\knowledge\atoms\`（markdown 真相源）。唯一标准：`{{PAIOS_ROOT}}\BLUEPRINT.md`。

## 何时触发

1. **写入（新建原子）**：一轮任务结束，出现下列情形**且确认有价值**时，主动问用户「这个经验要沉淀吗？」——
   - 踩坑后修复成功（重点：AI 之前错了什么）
   - 验证了可复用的方案/命令/配置
   - 明确了新的约束或边界
   - AI 犯了值得记住的错
   **只提议，不擅自写入**：未经用户点头不写入任何原子（连草稿都不写）；用户认可后再走「写入动作」。

## 价值门槛（写前先过，防知识库变垃圾场）

**只沉淀「换一个项目或半年后还用得上」的经验。**以下不入原子库：
- 纯项目内部细节（放项目 BLUEPRINT/README）
- 一次性调试痕迹、无复用价值的小折腾
- 同质重复、可并入既有 active 原子的（走「写入动作」里的并入，而非新建）

**宁可少而精，不可多而烂**：一条能救命的原子 > 十条谁都不看的原子。

## 归属判断筛子（写入前过）

- **换一个项目、或半年后还用得上 → 原子库**
- 只属于项目本身 → 项目 BLUEPRINT/README（不进原子库）
- 进度类（干到哪了）→ 项目任务清单/登记卡（不进原子库）

## 转正授权（红线变更 2026-09-02）

用户已授权 AI **按规则批量转正 + 抽查 + 可回滚**，取代旧「转正永远人工」。规则：
- **独立问题 + 明确技术层/场景边界 + 跨项目可复用** 的草稿 → 用 `paios_review_drafts` 批量转正
- **「跨项目可复用」按「可预见会再遇到」判定**（2026-09-02 校准）：抽象通用但预见不到再用场景的一律废弃——一次性领域情报（某平台数据源调研）、做完即止的工具配方（某类小工具技术选型）。判据问句：「用户半年内有没有可预见的第二次使用场景？」没有 → 废弃
- 同族但不同技术层（bash 转义 vs JS 转义）→ 各自独立转正，**不并入**
- 同质重复 → 并入已有 active 原子，不新建
- 纯项目私有 / 无跨项目价值 → 废弃（deprecated）
- **转正不是终局**：任何 active 原子可随时 deprecated→active 一键回滚；转正后向用户出示清单供抽查
- 需用户确认的例外：涉及「全局晋升规则」（写入 AGENTS.md 规则区）仍由用户决定

## 提炼规范（7 字段，一条原子一个问题）

```
【一句话结论】一行说清核心教训
【任务背景】当时要解决什么问题，前置条件
【人的判断】用户做出的核心判断、约束、需求
【判断理由】为什么这么定
【AI错误】AI 之前输出的错误方案；没有就写「无」，禁止编造
【修正方案】怎么修正的，关键改动点
【最终结果】拿到的真实可用输出
【适用边界】什么场景可用/不适用；禁止「通用」「都适用」这类空边界
```

- 每字段 1~3 句，禁止大段复制原文；当时只是猜想的写「当时推测」。
- 多个不相关教训拆成多条原子。
- **方案/决策/工作流类**（设计经验，无踩坑现场）：【AI错误】写「无」，重心放在【人的判断】为什么这么设计、【修正方案】可复用的做法/配方/流程、【适用边界】什么项目什么场景能抄。

## 写入动作

1. **先检索判重**：用核心关键词调 `paios_search_atoms`，阅读命中原子，判断语义是否重复——重复则不入库（可考虑更新既有原子或标记废弃旧条）；确属不同角度/结论才继续。
2. 组装 title（一句话）+ type（踩坑/方案/约束/决策/工作流）+ tags + body（7 字段）+ project + source_ref（sess_xxx 或 REQ 单号）。
3. 调 `paios_save_atom`，**默认 status=draft**（用户明确说「直接生效」才可 active）。
4. 若被「疑似重复」软告警拦截且**确认非重复**，带 `force=true` 重新提交；拿不准就把两条都给用户看。
5. 把返回的原子 ID 和转正入口（{{UI_URL}}）告知用户。
6. 若来源是某个会话，把 session_id 一并传入（自动清候选标记）。
7. **knowledge/ 目录的 git 推送由 Stop hook 自动完成**（同步→候选→备份→原子库推送四步），无需手动 push；若 hook 报推送失败（stderr 可见），按「PAIOS_GIT_PROXY 代理 + 直连重试」手动补推。

## 红线

- 转正按上方「转正授权」执行（可批量 + 抽查 + 可回滚）；涉及「全局晋升规则」（写入 AGENTS.md 规则区）仍由用户决定。
- 原始对话/日志永不入库；门禁拒绝时按提示修正重提，不许绕过。
- 来源是豆包等外部对话时 source=豆包，source_ref 写日期+主题。

## 复合原子拆分

当一条原子捆了多个不相关主题（如一条踩坑里同时含「进程权限」和「回执校验」两个教训），或它出现多个高相似并入去向时——先拆分再归族：

1. 把原原子按「一条原子一个问题」拆成 N 条子原子，每条完整 7 字段重写（标题、正文、边界各自独立）。
2. 调 `paios_save_atom` 逐条入库（force=true，source_ref 加 "(split from A-xxx)" 后缀，status 继承原原子）。
3. 调 `/api/atom_split`（POST {id, parts} 已由 save 完成 parts 时不必）或直接告知用户原原子已废弃——**实际废弃标记由 split 时把原原子 status 改 deprecated、split_into=[新id...] 完成**：用 `paios_promote_atom` 置 deprecated 后，在原原子文件 frontmatter 补 `split_into` 列表（或请用户在会话里确认后由你编辑该 md 文件——atoms 目录是真相源，允许 AI 编辑内容，状态流转仍走工具）。
4. 拆出的子原子再按相似度各自标注同族/合并。
